# Architecture

The operator journey is browser → loopback Next.js routes → transactional SQLite → server-side n8n dispatch → authenticated callback → validated plan → human review. With no generation webhook URL, the operator app uses clearly labeled deterministic fixture generation. The portfolio demonstration is a separate client-side, per-tab simulation; it does not use operator storage or provider credentials.

SQLite uses WAL, full synchronization, foreign keys, a busy timeout and immediate write transactions. Briefs, revisions, attempts, plans, activities and operation receipts commit together. HTTP/provider calls occur outside transactions. Current brief versions, active attempts and matching input revisions protect review and completion; unique operation keys prevent duplicate mutations. Plans and input revisions remain in history. New attempts clear the current-plan pointer. Stored malformed data is rejected rather than silently replaced.

Dashboard, review and detail routes are request-rendered. Client navigation refreshes after mutations. The access boundary combines loopback binding, Host checks, same-origin mutations and no permissive CORS. `DEMO_MODE` does not bypass these guards. JSON mutation/callback requests are limited to 256 KiB, measured from actual streamed bytes. This boundary does not identify users or protect against software running as the same local user. Shared/public operator hosting, multiple machines sharing a file and ephemeral disks remain outside scope.

Only the Groq adapter in `src/lib/provider-contract.ts` is implemented, using Groq's chat-completions API with strict structured output and model `openai/gpt-oss-120b`. That identifier is not an OpenAI API credential. Availability, pricing and quotas depend on the provider/account. The export keeps the existing direct HTTP provider call; it introduces no agent, tools or provider migration.

Webhook mode requires `N8N_WEBHOOK_URL`, `N8N_WEBHOOK_SECRET` and a distinct `N8N_CALLBACK_SECRET`. n8n holds three separate Header Auth credentials: dispatch authentication, Groq bearer authentication and callback authentication. The callback secret never appears in generation payloads or browser output. APP_URL determines the app's callback destination. n8n's `CAMPAIGN_CALLBACK_URL` must exactly match that destination; the workflow validates the pinned local hostname and callback path before making a provider call. It sends only to this validated destination and disables callback redirects. Compose pins the destination to the app service and binds both published ports to loopback.

n8n acknowledges dispatch before provider completion. Both provider success and failure produce a full contract envelope delivered by the authenticated callback node. Callback delivery has a 10-second timeout and up to three tries. An applied result and an expected duplicate/stale result return distinct 200 dispositions; unexpected store failures log a server error and return 500 for delivery retry. Malformed/incompatible envelopes do not mutate storage. Workflow validation or exhausted delivery errors fail the n8n execution; inspect execution status and logs. Payload saving is disabled, so durable recovery of the original output is not promised.

A dispatch transport error is uncertain: the server may already have accepted the request. The app logs that uncertainty and waits for a callback rather than immediately failing the attempt. After 120 seconds the existing expiry/retry flow can start a new attempt. Success and failure callbacks for expired, superseded or completed attempts cannot alter the current state. A rejected dispatch fails immediately. External approval notification is best effort after the local review transaction; it has no durable outbox, receipt or guaranteed redelivery.

Live n8n/Groq behavior and credential selection require separate acceptance. Configured environment variables establish configuration, not tested connection health.
